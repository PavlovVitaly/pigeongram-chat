# Pigeongram Chat

[Русская версия](README_RU.md) | [English version](README_EN.md)

## Назначение

`pigeongram-chat` — Go-приложение Pigeongram, которое предоставляет HTTP-интерфейс чата, WebSocket-соединения для обмена сообщениями в реальном времени и файловые операции через MinIO. Приложение также использует PostgreSQL для постоянного хранения пользователей, сообщений и сессий, Redis — для кэширования и обмена событиями между экземплярами сервера, а Prometheus — для метрик.

Описание составлено по текущему исходному коду и конфигурации проекта. Возможности, не подтверждённые кодом, здесь не предполагаются.

## Точка входа и общий поток запуска

Выполнение начинается в `cmd/server/main.go`, функции `main`.

На старте приложение:

1. читает флаги командной строки и формирует `serverID`;
2. создаёт подключение к PostgreSQL и при необходимости создаёт таблицы, индексы, функцию `get_recent_messages` и представление `active_users`;
3. пытается подключиться к Redis; при недоступности Redis переключается на кэш в памяти;
4. пытается подключиться к MinIO; при недоступности MinIO файловые маршруты не регистрируются;
5. создаёт репозитории PostgreSQL, WebSocket-менеджер и кэш;
6. запускает WebSocket-менеджер в отдельной горутине;
7. регистрирует HTTP-маршруты и оборачивает их middleware для HTTP-метрик;
8. начинает обслуживать HTTP-сервер.

Каталог `models` также содержит модели `User`, `Message` и `Session`; по структуре исходников он является отдельным набором типов.

## Архитектура и ответственность компонентов

### HTTP и представление

Пакет `web` обслуживает HTML-страницы и HTTP API. `renderTemplate` загружает шаблоны из `web/templates`. Основные страницы — вход, регистрация, чат и файловое хранилище.

### Авторизация и сессии

Сессия хранится в PostgreSQL, а её представление может кэшироваться. Идентификатор сессии передаётся в cookie `session_id`. `getUserFromSession` сначала проверяет кэш, затем обращается к `SessionRepository`, проверяет срок действия и при успешной проверке возвращает имя пользователя. `AuthMiddleware` перенаправляет запросы без действующей сессии на страницу входа.

Пароль при регистрации хешируется в `UserRepository` с помощью bcrypt. При входе хеш сравнивается с переданным паролем.

### WebSocket

`websocket.WebSocketHandler` проверяет сессию, переводит HTTP-соединение в WebSocket, создаёт `Client` и передаёт его менеджеру. Для каждого клиента запускаются `ReadPump` и `WritePump`.

`Manager` хранит подключённых клиентов, онлайн-пользователей и каналы событий. Он отвечает за:

- регистрацию и удаление клиентов;
- отправку истории сообщений новому клиенту;
- локальную рассылку сообщений;
- рассылку статусов онлайн;
- обработку событий файлов;
- обработку редактирования сообщений;
- сохранение сообщений и обновление кэша;
- обмен сообщениями и файловыми событиями через Redis Pub/Sub;
- периодический сбор части статистики базы данных.

### Хранилище данных

PostgreSQL-репозитории отделяют операции с базой от HTTP и WebSocket-кода. Кэш реализует общий интерфейс `cache.Cache`, поэтому менеджер может работать либо с Redis, либо с кэшем в памяти.

MinIO используется отдельно от PostgreSQL. Информация о файле передаётся как `FileInfo`, а сам объект хранится в MinIO.

## Модель данных

### PostgreSQL

Приложение создаёт таблицы:

- `users` — идентификатор, уникальное имя пользователя, хеш пароля, время последнего посещения и временные поля;
- `messages` — автор, текст, время сообщения, временные поля и признаки редактирования;
- `sessions` — идентификатор сессии, пользователь, срок действия и временные поля.

Связи `messages.user_id` и `sessions.user_id` ссылаются на `users.id`. В `config/database.go` также создаются индексы, SQL-функция `get_recent_messages` и представление `active_users`.

В `MessageRepository.GetRecent` выбираются последние сообщения с пользователями и затем возвращаются в порядке от старых к новым. При подключении нового клиента менеджер сначала пробует получить последние сообщения из кэша, а при отсутствии данных обращается к базе.

### Кэш

Кэш хранит:

- последние сообщения;
- пользователей;
- сессии.

Для сообщений используется ограничение в 100 элементов в реализациях кэша. Redis хранит значения с TTL и префиксом, заданными конфигурацией. Memory-кэш очищает устаревшие записи отдельной горутиной.

### Файлы

Ключ объекта MinIO формируется по схеме:

```text
chat-<chat_id>/<user_id>/<timestamp>-<filename>
```

`FileInfo` содержит имя, размер, время загрузки, тип содержимого, владельца, идентификатор чата и ключ объекта.

## Основные потоки данных

### Регистрация и вход

```text
HTTP-форма
  → RegisterHandler / LoginHandler
  → UserRepository и bcrypt
  → SessionRepository
  → кэш сессии
  → cookie session_id
  → /chat
```

При выходе `LogoutHandler` удаляет сессию из PostgreSQL, инвалидирует её в кэше и удаляет cookie.

### Подключение к чату

```text
GET /ws
  → AuthMiddleware
  → getUserFromSession
  → WebSocketHandler
  → NewClient
  → Manager.Register
  → sendMessageHistory
  → Client.Send
  → WebSocket WritePump
```

История берётся из кэша, а при промахе — из PostgreSQL. Перед отправкой она фильтруется и сортируется по времени.

### Отправка сообщения

`Client.ReadPump` принимает JSON в нескольких поддерживаемых формах: строка, объект с `text`, объект с `type` и `data`, а также объект с `username` и `text`. Пустые сообщения игнорируются, пробелы по краям удаляются, а текст длиннее 10 000 байт обрезается.

```text
WebSocket ReadPump
  → разбор и проверка текста
  → Manager.Broadcast
  → сохранение в PostgreSQL
  → обновление кэша
  → Redis Pub/Sub (если Redis доступен)
  → локальные WebSocket-клиенты
```

Сохранение в PostgreSQL и обновление кэша запускаются в отдельных горутинах.

### Редактирование сообщения

Сообщение с `type: "edit"` преобразуется в `EditRequest` и попадает в `Manager.EditMessage`. Репозиторий проверяет владельца сообщения, обновляет текст и поля редактирования, после чего менеджер рассылает обновлённое DTO локальным клиентам.

### Работа с файлами

```text
HTTP-запрос с session_id
  → FileHandler
  → проверка chat_id, имени или ключа
  → MinIOClient
  → временный URL / список / удаление / проксирование файла
  → FileEvents
  → WebSocket-клиенты и Redis Pub/Sub
```

Для удаления дополнительно проверяется, что ключ относится к указанному чату и что имя владельца в ключе совпадает с текущим пользователем.

### Обмен между экземплярами

Если Redis доступен, менеджер публикует сообщения в `chat:messages`, а события файлов — в `chat:files`. Входящие события от другого `serverID` рассылаются локальным клиентам. Реестр серверов хранится в ключах `server:<serverID>` с TTL и heartbeat.

## Конфигурация

### Флаги командной строки

`main` объявляет флаги `reset-db`, `use-redis`, `port` и `server-id`. Они влияют на сброс базы, выбор Redis, порт HTTP-сервера и идентификатор экземпляра соответственно.

### PostgreSQL

Конфигурация читает `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `DB_SSLMODE`, `PIGEONGRAM_RESET_DB` и `PIGEONGRAM_FORCE`.

### Redis

Конфигурация читает `REDIS_HOST`, `REDIS_PORT`, `REDIS_PASSWORD`, `REDIS_DB`, `REDIS_TTL`, `REDIS_PREFIX` и `REDIS_ENABLED`.

### MinIO

Конфигурация читает `MINIO_ENDPOINT`, `MINIO_ACCESS_KEY`, `MINIO_SECRET_KEY`, `MINIO_USE_SSL`, `MINIO_BUCKET`, `MINIO_REGION`, `MINIO_UPLOAD_EXPIRY`, `MINIO_DOWNLOAD_EXPIRY`, `MINIO_MAX_FILE_SIZE` и `MINIO_PUBLIC_URL`.

### Общие настройки

`SERVER_ENVIRONMENT` выбирает окружение. `DOMAIN` и `NGINX_PORT` используются функцией формирования публичного URL.

## Наблюдаемость

В `internal/metrics` объявлены метрики для HTTP-запросов, WebSocket-подключений и ошибок, сообщений, файлов, операций PostgreSQL, длительности операций, кэша и количества пользователей. HTTP middleware собирает метрики для обычных маршрутов; запрос `/ws` из него исключён.

Локальные конфигурации Prometheus и Grafana находятся в `docker_local/monitoring`.

## Границы и подтверждённые особенности текущего кода

- Если Redis недоступен, приложение продолжает работу с `MemoryCache`, но межсерверный обмен через Redis невозможен.
- Если MinIO недоступен, приложение продолжает запуск, но файловые маршруты не регистрируются.
- В `Dockerfile` healthcheck обращается к `/health`, однако в маршрутах `main` этот путь не зарегистрирован; `HealthCheckHandler` существует в `web/debug.go`, но в текущей функции `main` не подключён.
- `MessageRepository.DeleteOlderThan` оставлен с `TODO` и фактически ничего не удаляет.
- WebSocket-upgrader принимает любой origin (`CheckOrigin` возвращает `true`).
- Отладочные маршруты регистрируются только при `SERVER_ENVIRONMENT == "development"` и доступном MinIO; отдельные диагностические обработчики существуют, но не все подключены к маршрутизатору.
- `k3s`-манифесты и локальные конфигурации мониторинга находятся в этом репозитории, но их применение описывается проектом инфраструктуры, а не этим README.
